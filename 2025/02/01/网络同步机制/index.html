Week 1 探索阶段

Game Programming Patterns

原则

  • 抽象和解耦让扩展代码更快更容易，但除非确信需要灵活性，否则不要在这上面浪费时间。
  • 在整个开发周期中考虑并为性能设计，但是尽可能推迟那些底层的，基于假设的优化，那会锁死代码。
  • 快速地探索游戏的设计空间，但不要跑的太快，在身后留下烂摊子。毕竟，你总得回来打扫。
  • 如果打算抛弃这段代码，就不要尝试将其写完美。摇滚明星将旅店房间弄得一团糟，因为他们知道明天他们就走人了。
  • 但最重要的是，如果你想要做出让人享受的东西，那就享受做它的过程。

模式

重访设计模式：玩法

  • 命令：角色动作
  • 享元：各种地形
  • 观察者：成就
  • 原型：批量生产怪物
  • 单例：避免使用，引擎
  • 状态：连招

序列模式：时间

  • 双缓冲：两个舞台，一个亮一个不亮，保存状态
  • 游戏循环：帧同步的基础，更新和渲染如何同步解决卡顿问题
  • 更新方法：更新对象，让它更加真实。这个模式，以及游戏循环模式和组件模式，是构建游戏引擎核心的三位一体。

行为模式：剧本

  • 字节码：法术
  • 子类沙箱：用一系列由基类提供的操作定义子类中的行为，没太懂
  • 类型对象：创造一个类A来允许灵活的创造新“类型”，类A的每个实例都代表了不同的对象类型。

解耦模式：分成块好管理

  • 组件模式：允许单一的实体跨越多个领域而不会导致这些领域彼此耦合。
  • 事件队列：解耦发出消息或事件的时间和处理它的时间。两个队列
  • 服务定位器：提供服务的全局接入点，避免使用者和实现服务的具体类耦合。
  • 这就是服务定位模式的简短介绍——它解耦了需要服务的代码和服务由谁提供（那个具体的实现类）以及服务在哪里（我们如何获得它的实例）。这个也没咋懂

优化模式：加速游戏的中间层模式

  • 数据局部性：合理组织数据，充分使用CPU的缓存来加速内存读取。
  • 脏标识模式：将工作延期至需要其结果时才去执行，避免不必要的工作。
  • 对象池模式：放弃单独地分配和释放对象，从固定的池子中重用对象，以提高性能和内存使用率
  • 空间分区：将对象根据它们的位置存储在数据结构中，来高效地定位对象。

Gaffer on Games

UDP vs TCP

我的建议不仅是使用UDP，而且你的游戏协议应该只使用UDP。不要混用TCP和UDP！相反，你应该学习如何在你自己开发的基于UDP的自定义协议中实现所需的TCP特定功能。

关键在于，不要将游戏协议拆分到 UDP 和 TCP 上。保持游戏协议运行在 UDP 上，这样你才能完全控制发送和接收的数据，以及可靠性、顺序和拥塞避免机制的实现方式。

为什么用TCP反而对游戏不好：

  1. 如果发送的数据包非常小，TCP会一直等待不会发送，就会导致客户端玩家的输入不能很快响应；
  2. TCP对于乱序丢包有严格的重传机制，就导致延迟进一步增加，如果TCP判断网络拥塞则更严重，可能会减少窗口导致时延进一步上升；
  3. FPS对于实时数据不需要可靠有序的数据流；
  4. TCP同步会导致UDP丢包率增加；

Sending and Receiving Packets

介绍了一种与平台无关的方式来发送和接收数据包

Virtual Connection over UDP

建立虚拟连接只需要以下几点：建立连接的方法、过滤掉与连接无关的数据包，以及检测断开连接的超时机制。

Reliability and Congestion Avoidance over UDP

我们需要的是一种不同的可靠性。我们不希望所有数据都被视为可靠的有序数据流，而是希望以稳定的速率发送数据包，并在对方计算机收到数据包时收到通知。这样，对时间敏感的数据无需等待重发数据包即可通过，同时允许我们在应用层自行决定如何处理丢包。

What Every Programmer Needs To Know About Game Networking

每个玩家都做客户端，类似于哑终端，然后服务器运行游戏。

真正回答问题：为什么不用TCP？

本质： TCP 强制“时间顺序一致”，而游戏需要“时间连续流动”。

我们以FPS的一个场景举例，在某一时刻所有的玩家和ai都行动了，对应需要将位置同步，如果使用TCP。首先TCP的可靠传输会导致如果丢包，tcp会停止传输后面的包而进行重传，就会导致在这段时间服务器卡住，静默了（接收方 TCP 不会把后续数据交给应用层，Head-of-Line Blocking（HOL），数据被 TCP 内部缓冲住了），这个时候相当于所有的玩家都看不到反馈，然后重传结束后，突然对大量的包进行处理，这会导致玩家又马上看到ai或者其他玩家“闪现”，这样会非常影响游戏体验，RTT迅速变化，也被称为抖动（准确的说法是帧之间的可见状态更新时间不稳定，抖动的本质是：

平均 RTT 可能没变太多，

但时间间隔分布变了）。如果TCP因为丢包以为是网络拥塞，那么情况更糟糕，TCP会减少发送窗口，导致下一次发送的数据包数量更少，这就会导致玩家体感RTT增加（不是 RTT 增加。

而是：

发送速率下降
数据排队时间增加

RTT 是物理往返时间。

拥塞控制影响的是：

发送节奏

但体感上确实会像延迟变大），即使网络没有变化。

UDP 在游戏里的真实用法

不可靠 ≠ 乱发

真实情况是：

游戏不会直接裸用 UDP。

而是：

在 UDP 之上实现“游戏专用的轻量可靠层”。

它通常包含：

1️⃣ Sequencing（序列号）

每个包带：

作用：

  • 丢包检测
  • 乱序重排
  • 去重

2️⃣ ACK（选择性确认）

不是 TCP 那种“必须按顺序确认”。

而是：

  • 只确认收到的包
  • 可以 SACK（Selective ACK）
  • 不阻塞后续数据

关键点：

不可靠 ≠ 不可控
是“选择性可靠”

3️⃣ 轻量重传

重传只用于：

  • 关键事件（开枪）
  • 重要状态（死亡）

不会重传：

  • 高频位置更新

因为：

下一帧自然会覆盖上一帧

4️⃣ 时间戳 + 滑动窗口

每个包带：

作用：

  • 计算 RTT
  • 估计 jitter
  • 预测丢包
  • 调整发送速率

滑动窗口：

  • 控制在途包数量
  • 避免爆发式拥塞

你可以把现代 FPS 的 UDP 理解成：

“半个 TCP，但没有队头阻塞”

KCP 的定位

KCP 解决的是

在高丢包 + 高延迟环境下，提高吞吐和降低 RTT 波动。

它做了什么？

  • 更激进的重传
  • 更小的 RTO
  • 更快的拥塞恢复
  • 改进的窗口控制

简单说：

TCP 太保守
UDP 太裸
KCP 是折中

KCP 到底改了什么？（核心机制）

你问得非常专业，我们讲细一点。

KCP 相比 TCP 改的核心是 4 件事：

① RTO 计算更激进

TCP：

  • 最小 RTO 往往 200ms+
  • 丢包恢复慢

KCP：

  • 默认最小 RTO 100ms
  • 可以调更低
  • 更快触发重传

效果：

丢包恢复更快

② 快速重传机制不同

TCP：

  • 需要 3 个重复 ACK 才重传

KCP：

  • 可以更早触发
  • 支持 fast resend 参数
  • 不用等那么久
③ 无慢启动保守机制

TCP：

  • 慢启动
  • 拥塞避免
  • 拥塞窗口缩小

KCP：

  • 更激进
  • 可关闭拥塞控制
  • 追求低延迟而不是公平性

这很关键：

TCP 追求网络公平
KCP 追求游戏体验

④ 窗口机制不同

TCP：

  • 字节流
  • 顺序阻塞

KCP：

  • 分段
  • 无队头阻塞
  • 允许 out-of-order

一句话总结：

TCP 是为“互联网公平”设计的，KCP 是为“游戏低延迟”设计的

那 KCP 没解决什么？

⚠️ 非常重要：

KCP 没解决“游戏语义同步问题”。

什么意思？它只保证：

  • 字节流传输更稳定

但它不负责：

  • 角色预测
  • 插值
  • 帧推进
  • 回滚
  • Lag Compensation

KCP 是传输层工具，不是游戏同步架构

很多人搞混这一点。

帧同步 vs 状态同步 vs 混合同步

帧同步 vs 状态同步

世界计算架构的差异

如果是帧同步，一个玩家丢包必须等待所有人输入整齐（帧推进速度 = min(所有玩家网络速度)）

如果是状态同步，只有这个玩家卡。（状态同步服务器计算世界，客户端渲染+预测），状态同步如果丢一个包，做插值，服务器 20Hz 发状态，客户端 60Hz 渲染。客户端不会直接跳到最新状态。它会：

所以即使丢一帧：

客户端可以：

  • A → C 做插值

不会瞬移。

真正瞬移发生在：

连续丢包
或时间差太大

模型 是否需要预测
纯帧同步 不需要
状态同步 必须需要
半帧同步模型 本地输入缓冲优化（不是预测）

半帧同步

输入延迟 + 本地输入缓冲（Input Buffering）

传统帧同步的问题

如果A玩家延迟200ms，B玩家延迟20ms：

  • 每一帧都必须等200ms
  • 所有人都卡成200ms延迟

这体验极差。

解决办法：固定输入延迟（Input Delay）

例如：所有玩家统一延迟 100ms 执行输入

流程变成：

这叫：人为制造一个统一的输入延迟

这样：

  • 不再等最慢的人
  • 只等一个固定值
  • 延迟是稳定的（不会抖动）

这就是所谓的：本地输入缓冲优化，你按键之后不是立刻执行，而是排队，等到指定的“逻辑帧”才执行。

那为什么还需要预测？

因为 100ms 真的很明显。格斗游戏就是这样：

  • 要么接受100ms输入延迟
  • 要么用 rollback 模型

这就是 GGPO 的诞生原因。

GGPO 是什么？

GGPO 是：

一种“回滚式帧同步”

用在格斗游戏。它的核心：

  1. 仍然是帧同步（只传输入）
  2. 不等远端输入
  3. 先假设远端“没输入”
  4. 等真正输入到达
  5. 如果错了 → 回滚重算

这就是：

Rollback Netcode

和FPS不同：

  • 格斗游戏是确定性模拟（同样的输入序列 → 必定得到完全一样的结果）
  • FPS通常是状态同步 + 客户端预测

如果一个玩家 200ms 延迟，别人是不是刷新两次他才刷新一次？

不是。不会出现：

你60FPS，他30FPS

客户端渲染永远是本地60FPS。区别在于：

  • 他的输入到服务器慢
  • 服务器确认慢
  • 别人看到他的动作延迟

但：

  • 每个客户端都在自己本地正常渲染
  • 只是“看到他的位置更新慢”
  • 他收到服务器包慢，他发给服务器输入也慢
  • 所以：他看到所有人都慢半拍，别人看到他也慢半拍

游戏网络不是“数据传输问题”而是：时间控制问题；帧同步是：强一致时间。状态同步是：弱一致时间 + 服务器裁决。TCP 是：强顺序时间。UDP 是：不保证时间。游戏选择 UDP 是因为：我要自己决定时间怎么流动。

这些全部围绕一个核心：如何在时间不一致的情况下让玩家感觉一致？

UE5 是什么？

UE5 不是传输层工具。UE5 是：

游戏引擎 + 网络同步框架

它做的不是“传输字节”，而是：

  • Actor Replication
  • RPC
  • Server Authoritative 规则
  • 状态差量同步
  • 频率控制
  • 优先级排序

它在 应用层（Application Layer）。

名称 所在层级 是否理解游戏语义
UDP 传输层 ❌
KCP 传输层增强 ❌
UE5 网络 应用层框架 ✅

UE5 用哪种？

UE5 使用：

  • Server Authoritative
  • Actor Replication
  • Variable Replication
  • RPC

UE5 默认是：

Actor Replication = 状态同步模型

UE5 的机制是：

  • 服务器保存 Actor 状态
  • 周期性发送差量
  • 客户端接收并插值

它不是：

  • 每帧同步输入
  • 所有人等待一致

所以它是：

Server Authoritative + State Replication

关键理解

UE5 不是“只能状态同步”。而是：

它内置的网络框架是状态同步思想。

你可以自己写帧同步逻辑。但那是：

你绕开 UE5 的 replication 系统。

卡顿

玩家卡顿的本质：网络卡顿（数据到达间隔不稳定。表现为角色忽快忽慢，这基本就是 抖动（Jitter）+ 丢包 的表现。）；渲染卡顿（GPU/CPU 不够。表现为帧率低，帧时间不稳定）；同步模型导致的卡顿（比如：帧同步等输入。表现：整个世界暂停，这是架构问题。）

类型 本质 表现 根因
网络卡顿 抖动 / 丢包 忽快忽慢 / 瞬移 网络不稳定

架构卡顿 帧同步阻塞 世界暂停 同步模型

四者对比总结

问题 本质 是否稳定 画面表现 竞技影响 玩家体感
延迟 传播慢 稳定 平滑 时间差 不“卡”但慢
抖动 延迟波动 不稳定 忽快忽慢 大 明显卡
丢包 数据丢失 随机 瞬移 极大 非常卡
卡顿 更新不连续 不一定 停顿 取决来源 就是“卡”

现代 FPS 的对策

1️⃣ 对延迟

  • 客户端预测
  • 服务器时间回溯
  • Sub-tick 机制
  • 减少插值缓冲

目标：

降低“时间差感”

2️⃣ 对抖动

  • 插值缓冲（平滑时间线）
  • 动态插值窗口
  • 平滑算法（Hermite插值）
  • 丢包补偿预测

目标：

让延迟看起来稳定

3️⃣ 对丢包

  • UDP + 关键数据可靠通道
  • 状态冗余发送
  • Delta压缩 + 重发
  • 关键输入重复发送

目标：

保证关键数据一定到达

4️⃣ 对渲染卡顿

  • 帧时间锁定
  • 动态分辨率
  • 资源预加载
  • 多线程渲染

5️⃣ 对架构卡顿

  • 不用纯帧同步（FPS不用）
  • 状态同步 + 客户端预测
  • 局部回滚而非全局暂停

客户端预测为什么一定会产生误差？

客户端预测（Client Prediction）

意思是：

我不等服务器
我假设服务器会同意
直接本地模拟移动

也就是说：

这就是预测。

预测一定会错

为什么一定会错？

理论上：在完全确定性 + 无外界影响时可以。但 FPS 几乎不可能。为什么？因为：

  1. 服务器 tick rate 不等于客户端
  2. 其他玩家影响世界
  3. 物理模拟非确定性
  4. 浮点误差
  5. 网络延迟导致时间线不同步

即使你没撞墙，你客户端的时间点可能比服务器领先 40ms。在这 40ms 内：别人可能开枪打你。你客户端不知道。所以预测错是“时间线错位”造成的。不是逻辑错。

理论上如果：

  • 逻辑完全一致
  • 时间完全同步
  • 浮点完全一致

确实可以不出错。这就是 RTS 帧同步的原理（PS：纯帧同步不需要预测）。但 FPS 不行，因为：

  1. 服务器 tick rate 低（20Hz）
  2. 客户端帧率高（60Hz）
  3. 有物理碰撞
  4. 有其他玩家影响

举个例子：你预测向前。但在服务器世界里：

别人比你先到达那个位置

你客户端根本不知道。所以：预测必然会偏离。不是算法错。是信息不对称。服务器可能算出：

  • 你被撞了
  • 你被击退
  • 你卡在墙边

于是服务器发回真实位置。客户端发现：

自己预测错了

就要：

回滚 + 修正

这叫：

Reconciliation（校正）

回滚修正

客户端会保存：

当服务器告诉你：

在时间 T，你的位置应该是 X

客户端会：

  1. 回到 T
  2. 用服务器位置覆盖
  3. 把之后所有输入重新跑一遍

这叫：

回滚重演（Rollback + Replay）

  • 如果差距很小：玩家几乎感觉不到。
  • 如果差距很大：会出现小幅“拉回”。
  • 为什么不用慢慢滑？因为那会破坏物理一致性。

击杀计算

服务器时间回溯：只用于命中判定

Server Authoritative（服务器权威模型）防的是：

客户端作弊。

如果没有 Server Authoritative

假设客户端自己决定：

  • 我移动到了这里
  • 我血量是 100

作弊者可以：

  • 修改内存 → 无限血
  • 改射击判定 → 百发百中
  • 改移动速度 → 超人跑

你根本防不住。

Server Authoritative 做了什么？

核心思想：

客户端只发“输入”，服务器计算“结果”。

流程：

  1. 客户端发：
    • 我按了 W
    • 我开枪
  2. 服务器计算：
    • 你移动到哪里
    • 子弹是否命中
    • 扣谁的血
  3. 再广播给所有人

它防了什么？

攻击类型 是否能防
改血量 ✅
改伤害 ✅
改命中判定 ✅
改位置 ✅
加速外挂 大部分能防
透视外挂 ❌（这是客户端渲染问题）
自瞄 ❌（这是输入层作弊）

Server Authoritative 的代价是什么？

代价是：

增加了延迟 + 产生预测误差

因为：

  • 你按下开枪
  • 要发到服务器
  • 服务器算完
  • 再发回来

这就是：

网络 RTT 延迟

所以现代 FPS 必须：

  • 客户端预测（Client Prediction）
  • 服务器校正（Reconciliation）
  • 插值（Interpolation）

你可以这样理解

没有 Server Authoritative：游戏 = 本地单机 + 网络同步

有 Server Authoritative：游戏 = 远程执行 + 本地幻觉

Week 2 UE5网络

MOBA 能不能用 UE5？

先回答你最核心的问题：

MOBA 能不能用 UE5 做？

可以。完全可以。

UE5 是引擎，不是同步模型。

为什么几乎没听说 UE 做 MOBA？

因为历史原因 + 商业原因。

举例：

  • League of Legends 用的是自研 C++ 引擎
  • Dota 2 用的是 Source 2
  • 王者荣耀 用的是腾讯自研移动引擎

这些游戏都比 UE5 早。

那王者荣耀用什么做？

王者荣耀是：

自研 C++ 引擎 + 自研帧同步框架

因为：

  • 需要极端控制网络逻辑
  • 需要 deterministic
  • 需要低带宽
  • 需要移动端适配

那 UE5 为什么不常用于 MOBA？

因为 UE 默认网络框架是：

状态同步 + Server Authoritative

而传统 MOBA 是：

输入驱动 + Lockstep

UE 的 replication 系统并不适合做 lockstep。

你可以自己写一套帧同步系统。

但那基本等于：

不用 UE 内置网络系统。

关键理解

UE 是引擎。同步模型是架构选择。

就像：

  • UDP ≠ 同步模型
  • UE5 ≠ 状态同步
  • 只是默认设计哲学偏向 FPS

也有。服务器同样运行：

服务器 Tick 是“物理精度”：服务器 60 Tick 的作用是：

  • 更精确的碰撞检测
  • 更精确的移动计算
  • 更精确的命中判定
  • 更平滑的加速度计算

举个 FPS 例子：

  • 每 50ms 才更新一次位置
  • 子弹飞行可能直接“穿过去”
  • 高速移动容易漏判

这叫：

低 Tick 导致命中不精确

3️⃣ Tick 频率是否等于 FPS？

在客户端：

  • 默认 Tick 跟随帧率
  • 120 FPS → 120 Tick → 8.3ms

在服务器：

  • 可以限制最大 Tick Rate
  • 常见 30 / 60 Tick
  • 不一定等于客户端帧率

Tick 是：

世界逻辑更新频率

不是：

网络发送频率

服务器 Tick 是为“模拟精度”服务，网络频率是为“带宽控制”服务

网络系统在 Actor 框架中的位置

现在关键来了。UE 的网络系统不是“全局同步”。

而是：

每个 Actor 都可以被复制。

核心流程：

  1. 服务器持有 Actor
  2. 打开 bReplicates
  3. 变量标记 Replicated
  4. 服务器改变变量
  5. 客户端收到 Delta

UE 的网络同步单位是 Actor，不是世界。

UE 网络复制的是：AActor 及其标记为 Replicated 的属性。

Actor 是最小的“网络身份单位”。

每个 Actor 在网络上都有：

  • NetGUID
  • Channel
  • Role（Authority / SimulatedProxy）

Component 没有独立网络身份。

所以：

网络只能以 Actor 为边界。

服务器生成actor

服务器：

  1. 生成 Actor
  2. 为其分配 NetGUID
  3. 打开 ActorChannel
  4. 序列化初始状态
  5. 通过 NetDriver 发给客户端

客户端：

  1. 收到创建消息
  2. 根据类信息 Spawn 同类 Actor
  3. 赋值属性
  4. 标记为 SimulatedProxy

客户端：

客户端：

  1. 本地移动（预测）
  2. 发送输入给服务器

  • 重播未确认输入

层 类 职责
NetDriver UNetDriver 管理整个网络系统：所有连接，Tick 网络，发送/接收 Packet，调度 Replication
Connection UNetConnection 代表一个客户端连接，维护自己的 Channel 列表，处理可靠数据 ACK、重传、顺序维护
Channel UChannel 及子类 每个 Channel 是一条虚拟逻辑流，维护可靠序列号、逻辑阻塞、数据序列化
ActorChannel UActorChannel 专门用于 Actor：Replication（状态同步）、RPC、Delta Serialize、Dormancy 管理

重点：UDP 是底层运输工具，Channel 是可靠流，ActorChannel 是应用逻辑。

Channel 四个核心设计原因
  1. 序列号独立
    • 每个 Actor 的可靠流独立，丢包不会影响其他 Actor。
  2. 可靠性可控
    • 有些数据必须可靠（RPC），有些可以丢（位置更新）。
  3. 生命周期管理（Dormancy）
    • 不可见 Actor 可以暂停同步，节省带宽。
  4. 逻辑阻塞隔离
    • 某个 Actor 的包丢了只阻塞自己，不影响其他 Actor。
